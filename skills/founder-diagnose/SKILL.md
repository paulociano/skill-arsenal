# founder-diagnose

## Objetivo

Diagnosticar o gargalo principal de uma startup antes de aplicar frameworks, evitando tratar marketing, produto, posicionamento, distribuição ou preço como se fossem o mesmo problema.

## Quando usar

Diagnosticar gargalos de startups em produto, mercado, posicionamento, distribuição ou monetização antes de escolher uma intervenção.

## Princípio central

**Frameworks são ferramentas, não respostas. Primeiro diagnostique o problema; depois escolha uma única ferramenta principal.**

## Cinco modos de falha

1. **Product** — pessoas testam e não continuam usando.
2. **Market** — não existe dor/urgência suficiente para gerar comportamento de compra.
3. **Messaging / Positioning** — o produto pode ser bom, mas o cliente entende errado o que é ou para quem serve.
4. **Distribution** — cliente certo existe, mas não encontra a oferta.
5. **Pricing / Monetization** — existe interesse, mas valor percebido, modelo de cobrança, embalagem ou preço impedem compra.

## Workflow

1. Pedir/usar evidência concreta: uso, churn, conversas, vendas, CAC, origem de leads, objections, pricing, comportamento pós-compra.
2. Separar sintoma de causa.
3. Classificar o gargalo dominante entre os cinco modos.
4. Escolher **uma skill primária** e, no máximo, uma secundária sequencial.
5. Definir uma ação concreta e realizável para gerar evidência nova nesta semana.
6. Se os dados não permitirem diagnóstico, mandar observar a realidade antes de aplicar mais frameworks.

## Roteamento para o Arsenal

- **Market / problem uncertainty:** `customer-interview` → `jtbd-framing` → `experiment-design`.
- **Product / value hypothesis:** `idea-refine` + `experiment-design`.
- **Messaging / positioning:** `writing-quality`, `voice-builder`, `social-post-review` quando aplicável; usar pesquisa competitiva atual quando o contexto exigir.
- **Distribution:** `niche-research`, `content-matrix`, experimentos de canal com `experiment-design`.
- **Pricing / monetization:** pesquisa de WTP e testes de embalagem/preço; usar `customer-interview` + `experiment-design` e pesquisa externa atual quando necessário.

## Regra do one-skill

Não empilhar 3–4 frameworks para parecer completo. Um diagnóstico deve terminar com uma ferramenta principal, uma secundária apenas se houver sequência clara, e um próximo passo.

## Quando nenhum framework serve

Se várias tentativas não mudam evidência, se o problema é operacional/equipe/timing, ou se faltam observações básicas, parar o framework e coletar dados reais.
