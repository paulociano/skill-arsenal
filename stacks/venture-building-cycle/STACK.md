# Venture Building Cycle

## Objetivo

Conectar criação de negócio, validação, prototipagem e lançamento em um ciclo coerente de redução de incerteza, usando os owners especializados do Arsenal em vez de uma mega-skill de startup.

A unidade de progresso não é "quantos documentos foram produzidos", mas **qual incerteza relevante foi reduzida e qual compromisso real foi observado**.

## Quando usar

- criar uma startup ou nova empresa;
- transformar uma ideia em negócio testável;
- venture studio / corporate innovation;
- explorar novo produto ou modelo de negócio;
- construir e validar MVP/protótipo;
- preparar primeiros clientes e GTM;
- revisar se uma startup deve perseverar, iterar, pivotar, pausar ou encerrar uma hipótese.

Para uma tarefa isolada, usar somente a skill owner correspondente.

## Princípios

1. **Assumptions before artifacts** — explicitar o que precisa ser verdade antes de investir em deck, marca ou produto completo.
2. **Riskiest assumption first** — testar primeiro a incerteza que mais destrói a tese se estiver errada, não a mais confortável.
3. **Evidence ladder** — opinião e elogio têm menos força que comportamento, esforço, acesso, introdução, piloto, pré-compra, contrato ou uso recorrente.
4. **Cheapest credible test** — escolher o experimento de menor custo que produza evidência adequada à decisão.
5. **Prototype fidelity follows uncertainty** — protótipo deve ser tão real quanto necessário para testar a hipótese, não tão completo quanto tecnicamente possível.
6. **Business model is a hypothesis system** — segmento, problema, canal, proposta, preço, custos e operação são hipóteses conectadas, não campos preenchidos uma vez.
7. **Economics before scale** — crescimento sem entender contribuição, custo de servir, retenção e caixa pode amplificar um modelo ruim.
8. **Decision gates, not theater** — cada fase termina em decisão baseada na evidência disponível, com incerteza explícita.
9. **No universal startup recipe** — número de entrevistas, duração de sprint, TAM mínimo, CAC/LTV, margem ou estágio de captação dependem do negócio e da evidência.
10. **Human judgment remains owner** — o sistema organiza evidência e opções; não declara automaticamente que um negócio "vai dar certo".

## Venture evidence ledger

Quando a iniciativa justificar estado persistente, manter um ledger leve:

- hipótese;
- categoria: problem, customer, solution, channel, monetization, feasibility, viability, operations;
- importância;
- evidência atual;
- fonte/data;
- experimento;
- threshold/decision rule definido antes do resultado quando aplicável;
- resultado;
- decisão;
- próximo teste.

Não transformar score agregado em verdade sobre a startup.

## Workflow

### 1. Frame the venture
Usar `idea-refine` para:
- problema/outcome;
- usuário e comprador;
- alternativas atuais;
- proposta inicial;
- restrições;
- assumptions críticas;
- non-goals.

Se já existe startup em operação, começar com `founder-diagnose`.

### 2. Map the business hypothesis
Representar somente as dimensões que podem mudar a decisão:
- segmento/ICP;
- problema/JTBD;
- solução/wedge;
- distribuição;
- monetização;
- custos/capacidade;
- vantagem/diferenciação;
- riscos de execução.

Canvas é ferramenta de explicitação, não evidência.

### 3. Rank uncertainty
Priorizar assumptions pela combinação de:
- dano se falsa;
- incerteza real;
- custo de aprender tarde;
- dependências.

Identificar 1–3 assumptions fatais antes de construir.

### 4. Customer evidence
Usar `customer-interview` e, quando necessário, `first-customer-research`.

Separar:
- problema observado;
- workaround;
- frequência/urgência;
- processo de compra;
- orçamento/WTP;
- usuário vs comprador;
- compromisso real.

Não tratar intenção declarada como compra.

### 5. Design the experiment
Usar `experiment-design`.

Para cada assumption crítica:
- hipótese falsificável;
- sinal;
- experimento;
- custo/tempo;
- critério de decisão;
- evidência esperada;
- próximo passo se apoiar ou contradizer.

Preferir experimento reversível e barato.

### 6. Choose prototype fidelity
Escolher o artefato mínimo capaz de testar a hipótese:
- entrevista/conceito;
- storyboard;
- landing page;
- clickable prototype;
- concierge/manual service;
- Wizard-of-Oz;
- technical spike;
- functional MVP;
- pilot.

Não construir backend completo para testar mensagem; não usar mock estático para provar feasibility técnica.

Para web prototype, rotear a `web-design-engineer` ou stack apropriada somente quando implementação real agregar sinal.

### 7. Define the wedge
Antes do MVP:
- hero workflow;
- usuário inicial;
- job/evento específico;
- core value;
- time-to-value;
- non-goals;
- trust/safety requirements;
- instrumentação mínima;
- kill/revisit criteria.

Usar `to-spec` somente quando a solução estiver suficientemente decidida.

### 8. Monetization hypothesis
Separar:
- quem paga;
- value metric;
- modelo de cobrança;
- recorrência;
- custo variável/de servir;
- package/tier;
- price hypothesis;
- upgrade trigger;
- WTP evidence.

Preço de concorrente é âncora de mercado, não prova de willingness-to-pay.

Quando custo recorrente é material, evitar modelos que desconectem receita do custo sem explicitar o risco.

### 9. First customers and GTM
Usar `first-customer-research` para design partners/beta/primeiros clientes.

Explorar canais como hipóteses. Para os mais plausíveis:
- target;
- message;
- offer;
- channel;
- test;
- budget/time;
- metric;
- stop/continue rule.

Não escolher canal apenas porque é popular.

### 10. Economics and operating model
Construir modelo proporcional ao estágio:
- revenue drivers;
- gross/contribution margin quando aplicável;
- acquisition cost assumptions;
- retention/churn;
- cost to serve;
- headcount/operating costs;
- burn/runway;
- cenários e sensibilidades.

Usar `scenario-forecasting` quando projeções ajudarem a decisão.

Toda projeção deve separar input observado de assumption.

### 11. Launch and observe
Definir:
- activation/value event;
- retention/repeat behavior;
- revenue/commitment signal;
- quality/trust guardrails;
- feedback channel.

Para produto real, usar owners de implementação e `production-go-live` conforme risco.

### 12. Venture review
Comparar evidência com a tese e decidir:
- persevere;
- iterate;
- pivot;
- pause;
- kill hypothesis/venture.

Não exigir decisão binária prematura. Registrar o que mudou na crença e qual evidência faria revisar novamente.

## Prototype ladder

Use a menor fidelidade que responda à pergunta:

| Incerteza | Teste inicial plausível |
| --- | --- |
| problema existe? | entrevistas/comportamento passado |
| mensagem desperta ação? | landing/message test |
| workflow é compreensível? | storyboard/clickable prototype |
| usuário obtém valor? | concierge/Wizard-of-Oz |
| tecnologia funciona? | technical spike |
| uso se repete? | functional MVP/pilot |
| alguém paga? | pricing conversation, deposit, preorder ou transação apropriada |
| canal escala? | teste limitado com economics observáveis |

A tabela é orientação, não regra automática.

## Innovation / corporate venture

Em empresa estabelecida, adicionar:
- sponsor/decision owner;
- strategic fit;
- constraints de marca/compliance;
- acesso a canal/dados/ativos;
- conflitos com negócio atual;
- critérios de transferência para operação;
- kill/scale gate.

Não usar "inovação" como justificativa para dispensar evidência.

## Gate de escala

Antes de aumentar gasto, headcount ou complexidade, verificar:
- sinal de valor repetido;
- segmento suficientemente claro;
- motion de aquisição observável;
- economics minimamente compreendidos;
- capacidade operacional;
- riscos críticos conhecidos;
- hipótese explícita para o próximo investimento.

Ausência de evidência não é evidência de fracasso, mas também não autoriza certeza.

## Origem metodológica

Síntese independente de padrões recorrentes observados em projetos open source de venture building e startup validation, incluindo:
- LucaKnobel/idea-validation-platform
- Faeif/casekit
- aoli0919/startup-validation-skills
- nimitbhargava/testing-business-ideas-skill
- agentii-ai/pmf-kit
- impactbrussels/FounderOS
- goabego/ai-gtm-playbook
- Kappaemme-git/codex-startup-pricing-lab
- isumitsoni/claude-code-for-founders

A adaptação preserva risk-first validation, evidence ledger, experiment gates, prototype fidelity, PMF specification, channel tests e economics, removendo installers, agentes específicos, números universais, scores automáticos e claims não verificados.
